2. New bugs / residual risks
 1. Hit→open TOCTOU serves 500 instead of refetch/404 — files_http.rs:217-221 (prepare checks byte_len) and :276-296 (open in a second spawn_blocking) are two unguarded steps. Eviction/delete between them yields open_reader→None, get→None, then :293 Err(ApiError::internal()) → 500 for a routine race. Low. Should re-enter the refetch path (or 404), not 500.
 2. serve_file_named Location built from raw path input — files_http.rs:374-380 format!("/files/{id}") with attacker-influenced id. A %0D%0A-decoded CRLF in id reaches header construction; depending on axum's tuple-responder validation this panics the task or errors. Low (single-task DoS at worst). Validate/encode id before reflecting.
 3. Cold-GET origin failure surfaces 500, not 404 — files_http.rs:260 swallows PortError::Validation (dead origin, SSRF-blocked, oversize, REMOTE_CACHE_DISABLED, budget-exhausted) and falls through to :266 ApiError::internal(). Proxy correctly returns 404 (:453,456-457). Inconsistent + 500-telemetry pollution. Low/medium correctness.
 4. remote_cache_touch failure fails the hit closed as 500 — :227-230 map_err(...)? turns an LRU-write failure into a failed image load. Availability trade-off of the required touch; consider serve-stale + log. Low.
 5. Unbounded spawn_blocking on the hit path — only cold fetches share the 8-slot bound; cache/durable hits still enqueue one blocking task per request with no bound. Under hit flood the blocking pool (default 512) queues unboundedly. Plan-compliant (only cold path needed a bound), but residual DoS amplifier combined with #4's per-hit write txn. Low.
 6. Slot × reservation interaction under slow origin — each parked cold fetch holds its slot and a full max_file_size reservation (files_http_cache_hit.rs:679-680 pins this). 8 stalled origins (20 s total_timeout, errors.rs:37) pin 8×max_file_size phantom + 8 blocking threads; sustained cold-miss rate collapses to ~0.4 rps with 429s. Intended fail-closed, but flag for capacity tuning. Info.
 7. Memory: proxy 8 MiB cap is per-fetch heap, chunked path doubles it transiently — framing.rs:137-159: encoded body_raw (up to cap+4 KiB) + decoded body coexist → ~16 MiB per chunked proxy fetch; 8 slots → ~64–128 MiB worst case. fetch.rs:210-214 admits origin fetch still whole-buffers max_file_size via SafeHttpClient before disk staging. Plan-explicitly allowed ("cap may remain, read happens off the worker"), recorded here as the follow-up, not a regression. Info.
 8. Proxy url length unchecked — fetch path caps at 1024 chars (fetch.rs:52-56); proxy (files_http.rs:425-434) only checks scheme, then send.rs:243 write!s the full URL into the request line. A multi-MB query allocates per-request on a blocking thread. Low; add the same 1024 cap.
 9. Proxy 400-vs-404 oracle — SSRF-blocked/dead origin → 404 (:453), wrong-type → 400 (:470), live image → 200. Lets an unauthenticated caller distinguish "host serves image/*" from "blocked/dead" (image-server port-scan oracle). Standard media-proxy exposure, unchanged from upstream shape; noted. Low.
10. Unauthenticated GET = DB write — finding-5 compliance costs one redb write txn per /files hit. Expected, but combined with no Cache-Control on /files (proxy sets max-age=31536000, immutable at :479-482; files sets none) every image load re-hits origin server + write txn. Perf, not security.
11. Background fetch jobs bypass the 8-slot bound — the semaphore guards only serve_file/proxy_media entry; inbox/job-triggered fetch_and_index_remote_media calls reserve without a slot. A remote-mention flood can still stack blocking fetches outside the bound. Out of slice-3 scope; flag for follow-up. Low.
3. DoS / correctness notes
- Slow-origin worker exhaustion: closed — blocking network + fs work is on spawn_blocking threads, cold/proxy concurrency capped at 8 with non-blocking 429 + Retry-After: 5. Remaining pressure points are the blocking pool queue on hits (§2.5) and slot-holding during 20 s stalls (§2.6).
- Memory exhaustion: bounded but large — proxy ≤ ~8 MiB (16 MiB chunked transient) × 8; origin refetch ≤ max_file_size whole-buffered on a blocking thread (code comment fetch.rs:210-214 discloses the non-streaming transport). No unbounded Vec growth; framing.rs enforces Content-Length pre-check (:77-85), running cap (:142-146), 32 KiB header cap (:45-47), 8 interim blocks (:27), chunked decode budget (:236-245).
- SSRF: no bypass found — literals checked pre-DNS, DNS addrs all checked post-resolve, redirects re-resolved/re-checked, downgrade rejected, userinfo rejected, connect pinned to validated addr (send.rs:217-220, curl --resolve at :323 + --noproxy * at :52-54), per-op 10 s / total 20 s / DNS 5 s timeouts. Gaps are policy-level only: any public-IP port reachable via GET (port-scan of public hosts), allowed_hosts/allow_private_ips operator exemptions — both intentional.
- Header injection: safe — reflected Content-Type goes through mime.parse::<HeaderValue>() with octet-stream fallback (:335-339, :474-478); stored/proxied mimes originate from sniff_mime or its strip+lowercase, never raw caller input. Content-Disposition: attachment carries no filename (no injection surface).
- Path traversal: safe — storage.rs:27-32 validate_hash (4–128 alnum) gates object_path/temp_path/sidecar_path; blob keys are SHA-256 hex; open traversal test at storage.rs:507 passes.
- Range: absent by design (plan §6); no 206/304 support — full re-download per GET. No security impact.
