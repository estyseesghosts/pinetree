## Decisions and DIVERGENCES (recorded)

- **Ticket `id`** (beyond the guide's §3.3 sketch): upstream's packed `InviteCode` has `id` and `invite/delete` takes `inviteId`, so `InviteCode` carries an aidx id and list pagination is id-ordered. DIVERGENCE from the guide's type list only.
- **`deleteInvite` log row**: guide §3.2 names it; upstream logs nothing on `invite/delete`. Pinetree writes the row (audit) — a pinetree-only action, like `createAccount`.
- **`createAccount` row details** carry `userId: null` (account ids are store-generated and cannot be referenced from a row built before the insert) + `userUsername`/`userHost: null`. Same convention as the CLI `setRole` rows from WP1.
- **`admin/accounts/create`**: upstream's first-setup bootstrap (`setupPassword` / `INCORRECT_INITIAL_PASSWORD`) has no pinetree equivalent (CLI `create-account` bootstraps); `setupPassword` is accepted and never consulted — exactly what upstream does for an authenticated admin. Upstream's per-endpoint `ACCESS_DENIED` UUID (`1fb7cb09-…`) is not copied; §16 one-UUID-per-code keeps pinetree's `56f35758-…`.
- **§9.1 default policy (recorded choice)**: invite creation is moderator-only (upstream `canInvite` default `false`) via both `invite/create` and `admin/invite/create`; unlimited count (upstream `inviteLimit: 0`) → `invite/limit` answers `{remaining: null}` and `EXCEEDED_LIMIT_OF_CREATE_INVITE_CODE` (`8b165dd3-…`) is defined-but-unused. The per-user cap option stays open (needs a limit store).
- **`admin/update-meta` field subset**: `disableRegistration` + `blockedHosts` only; other fields are refused by the strict field check (400), never silently ignored (a 200 that stores nothing would be a lie). WP6/WP5 extend the set. `blockedHosts` is stored + normalized now (upstream `admin/update-meta.ts:260`) and enforced from WP5.
- **`admin/invite/list` `sort`** maps upstream's switch verbatim (`+createdAt` = id DESC newest-first — the standard Misskey convention, `users.ts:77` same).
- **`expiresAt` parsing**: RFC3339 or ISO naive (treated as UTC) — upstream accepts any `Date.parse` string; unparsable input answers `INVALID_DATE_TIME` (400).
- **Conformance I3 scope**: the registration *gate* is application logic (`AppServices::signup`), so the store contract case covers persistence + the `updateServerSettings` row, and gate enforcement is asserted at endpoint level (documented in `docs/persistence-conformance.md` §17).
