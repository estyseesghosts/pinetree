## What changed

**Slice A — index + query** (`docs/replies.md` §§3–5):
- `NoteStore::notes_by_reply(reply_id, cursor)` contract (candidate-scan limit,
  exclusive cursor bounds, deleted excluded, no existence check). redb
  `NOTES_BY_REPLY ((parent, child))`, range-`rev()` newest-first via `matches_cursor`.
- Versioned crash-resumable backfill: new `META` table,
  `migration:notes_by_reply:v1` done marker + progress cursor, 500 rows/batch,
  index inserts + cursor in one txn, marker only with the final batch. Runs in
  `RedbStore::open()` before serving. Test hook `remove_reply_index_for_test`
  simulates legacy DBs.
- `AppServices::note_replies` is now a bounded visibility-aware scan loop
  (batch 50, page clamped 1..=100 default 10, original `sinceId`/dates kept,
  strict-`untilId`-advance guard against backend bugs). `note_children`,
  `note_renotes`, `note_conversation` untouched.
- Delete unified: the two copy-pasted delete bodies are now one
  (`delete_note` delegates to `delete_note_in_txn`); first delete of a note with
  `reply_id` saturating-decrements the parent counter + drops the index row in
  the same txn; pending children drop their pending row; descendants keep
  `reply_id`; repeats stay `NotFound` (no double-dec).
- `Note::is_reply()` (resolved OR pending); all five `withReplies=false` sites
  (local/hybrid/channel/user_notes) use it.

**Slice B — unresolved parents** (§6):
- `Note.reply_parent_uri` (`#[serde(default)]`, ≤2048, internal-only, never packed
  or rendered) + `CreateNoteInput.reply_parent_uri` (inbox-only: local
  `create_note` rejects it; store rejects both-set; `validate_common` rejects
  both-set on the row).
- Fail-closed reads: `is_visible` returns false while pending (detail, profiles,
  search, timelines, feeds, AP object endpoints, streaming eligibility — all gate
  on this one predicate; store-level reads unaffected).
- Inbox preserves unresolved `inReplyTo` (trimmed, non-empty) + enqueues a
  URI-keyed `ReplyParentResolve` job atomically; arrival of a note whose URI has
  waiters enqueues another. No inline fetch, no startup sweep.
- New `inbound::replies`: `build_reply_parent_resolve_job` (key
  `reply-resolve:{uri}`), `resolve_reply_parent` (cached lookup via
  `resolve_note_target_id`, else SSRF-guarded fetch+cache; canonical-match link;
  alias re-key; per-child cycle/mismatch skip with entry kept; continuation on
  full batches), `repair_unresolved_reply_parents` (sequential, clamped 1..=5000,
  marks only fetched docs that still declare `inReplyTo`, never text-guesses).
- Worker dispatch: payload errors quarantine; unavailable parent retries with
  standard backoff (quarantine past budget, entry kept); continuations via Fanout.
- `NoteStore::{pending_reply_children, link_pending_reply, set_pending_reply_parent}`
  (link = reply_id + clear pending + adopt author + re-narrow + counter + index
  swap, one txn, idempotent; Validation on mismatch/cycle).
- `PINETREE_REPLY_REPAIR_LIMIT` startup gate (off by default) in `main.rs`.
- Renderer defense: pending notes render no `inReplyTo` (AP endpoints 404 them
  anyway via `is_visible`).

**Slice C — regression hardening**: outbound `inReplyTo` = direct parent canonical
(unchanged code, new test incl. pending non-leak); children/conversation semantics
pinned by R11/R12.

**Decisions worth recording**: linking to a *deleted* parent is allowed (steady
state matches create-then-delete ordering; counters stay exact); alias-URI
children are re-keyed to the fetched canonical before linking; repair marks make
historical roots transiently invisible until the resolver (enqueued atomically)
links them.
